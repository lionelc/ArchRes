# Prior work on performance-gap analysis, and what causal analysis adds

Literature map for the CauSE 2027 paper (`paper/`), assembled 8–11 Nov 2026.
Every work below was checked against a publisher page, DBLP, arXiv or an author page; the
verification tag of each BibTeX entry is in `paper/refs.bib`. Numbers quoted here are the
papers' own headline figures.

## 2. Notes per paper

### Gaps between implementations

- **Jangda, Powers, Berger, Guha. Not So Fast: Analyzing the Performance of WebAssembly vs. Native Code. USENIX ATC 2019, pp. 107–120.**
  Runs unmodified Unix applications compiled to WebAssembly in browsers; they are on average 45% (Firefox) to 55% (Chrome) slower than native code.
  Causes are split into missing optimizations and code-generation issues on one side and limits inherent to the platform on the other.
  *Relevance:* an informal fixable/architectural split. The scope of "inherent" is what the platform requires, an implicit contract.
- **Zhang, Zhang, Portokalidis, Xu. Towards Understanding the Runtime Performance of Rust. ASE 2022. doi:10.1145/3551349.3559494.**
  Micro-benchmarks implemented identically in Rust and C; Rust carries a 1.77× average overhead.
  The overhead comes mainly from compiler-inserted run-time checks (out-of-bounds checks alone account for 52.7%) and language restrictions.
  With the checks disabled and the restrictions loosened, Rust is indistinguishable from C.
  *Relevance:* an interventional attribution, one mechanism at a time, on micro-benchmarks. Whether disabling checks is admissible is exactly a contract question.
- **Yuan, Wang, Zhou, Liu, Peng. Where Does the Performance Go? Understanding and Recovering Performance Regressions in C-to-Rust Translation. arXiv:2610.23044, Oct 2026.**
  20 C projects and their c2rust translations. Translated Rust is more than 3% slower on 12 of 19 operations, by up to 62.2%.
  Execution-cost profiles, optimized LLVM IR and optimization remarks are compared per pair, giving nine recurring issues.
  PerfR then uses rule-guided LLM rewriting to recover performance: 40 of 41 held-out operations get faster, 18 of them faster than C.
  *Relevance:* the closest recent work, a reimplementation-versus-reference gap study. It is descriptive diagnosis followed by repairs, i.e. witnesses. It does not address gaps that no rewrite closes.
- **Gaffney, Prammer, Brasfield, Hipp, Kennedy, Patel. SQLite: Past, Present, and Future. PVLDB 15(12):3535–3547, 2022.**
  DuckDB serves as the reference point. VDBE profiling locates SQLite's OLAP bottlenecks, and Bloom-filter join processing (shipped in 3.38.0) makes SQLite up to 4.2× faster on SSB.
  The remaining gap is called somewhat expected, since DuckDB is designed for OLAP. Further changes must cause no significant regressions, must justify their source and binary size, and must keep backward and cross-platform compatibility.
  *Relevance:* a textbook informal architecture contract, and it concerns our reference engine.
- **Marr, Daloze, Mössenböck. Cross-Language Compiler Benchmarking: Are We Fast Yet? DLS 2016, pp. 120–131.**
  14 benchmarks over a common set of abstractions, ported across languages, to compare language implementations. *Relevance:* quantifies gaps without attributing them.
- **Lee et al. Debunking the 100X GPU vs. CPU Myth. ISCA 2010, pp. 451–460.**
  Published 10–1000× GPU-over-CPU claims shrink to 2.5× on average once both platforms receive appropriate optimizations. The paper also analyzes which architectural features account for the remainder.
  *Relevance:* a gap was largely fixable, and closing it was the evidence. That is a witness.
- **Satish et al. Can Traditional Programming Bridge the Ninja Performance Gap for Parallel Computing Applications? ISCA 2012, pp. 440–451.**
  The gap between naive and best-optimized code averages 24× (up to 53×); algorithmic changes plus compiler technology bring it to 1.3×.
  *Relevance:* again a witness. "Ninja gap" is an established name for a closable gap.
- **Kersten, Leis, Kemper, Neumann, Pavlo, Boncz. Everything You Always Wanted to Know About Compiled and Vectorized Queries But Were Afraid to Ask. PVLDB 11(13):2209–2222, 2018.**
  Both query-processing paradigms are implemented in one test system, with the same algorithms, data structures and parallelization, so that implementation choices do not obstruct a comparison of architectures.
  *Relevance:* a controlled design separating architecture from implementation, achieved by building variants. We obtain variants by switches and knock-outs instead.
- **Harizopoulos, Abadi, Madden, Stonebraker. OLTP Through the Looking Glass, and What We Found There. SIGMOD 2008, pp. 981–992.**
  Rather than only profiling Shore, the authors remove features one at a time, keeping a working system after each step. The overheads they identify explain a factor of about 20.
  *Relevance:* interventional decomposition by sequential removal. Shares from sequential removal can depend on the order when mechanisms interact; our 2^k design measures the interactions.

### Localizing performance changes (shared history)

- **Heger, Happe, Farahbod. Automated Root Cause Isolation of Performance Regressions During Software Development. ICPE 2013, pp. 27–38.** Performance unit tests plus bisection over revision history.
- **Luo, Poshyvanyk, Grechanik. Mining Performance Regression Inducing Code Changes in Evolving Software (PerfImpact). MSR 2016, pp. 25–36.** Search-based input profiling finds inputs that are slower in the new release; change-impact analysis ranks the responsible changes. Poshyvanyk is on the CauSE programme committee.
- **Mühlbauer, Apel, Siegmund. Identifying Software Performance Changes Across Variants and Versions. ASE 2020, pp. 611–622.** Locates performance changes over configuration variants and commit history.
- **Jung, Hu, Arulraj, Kim, Kang. APOLLO: Automatic Detection and Diagnosis of Performance Regressions in Database Systems. PVLDB 13(1):57–70, 2019.** Detects regressions across DBMS versions (SQLite, PostgreSQL), then diagnoses them by commit bisection and statistical debugging, i.e. correlation-based predicates.
- **Sambasivan et al. Diagnosing Performance Changes by Comparing Request Flows (Spectroscope). NSDI 2011, pp. 43–56.** Compares request flows from two periods and ranks changes by their expected contribution.
- **Daly, Brown, Ingo, O'Leary, Bradford. The Use of Change Point Detection to Identify Software Performance Regressions in a CI System. ICPE 2020, pp. 67–75.** E-Divisive change-point detection at MongoDB.
- **Zeller. Yesterday, my program worked. Today, it does not. Why? ESEC/FSE 1999, LNCS 1687, pp. 253–267.** Delta debugging over the changes between two versions.

*Shared point:* reverting a change is the intervention, which exists only because the two versions share a history. A reimplementation and its reference have no common history, so we intervene on mechanisms inside each engine.

### Differential and metamorphic performance testing

- **McKeeman. Differential Testing for Software. Digital Technical Journal 10(1):100–107, 1998.** Comparable systems as each other's oracle.
- **Barany. Finding Missed Compiler Optimizations by Differential Testing. CC 2018, pp. 82–92** (best paper). Compares the code different compilers generate for the same program.
- **Theodoridis, Rigger, Su. Finding Missed Optimizations through the Lens of Dead Code Elimination. ASPLOS 2022.** Uses dead-code markers as a differential signal across compilers and optimization levels.
- **Liu, Zhou, Arulraj, Orso. Automatic Detection of Performance Bugs in Database Systems using Equivalent Queries (AMOEBA). ICSE 2022, pp. 225–236.** Semantically equivalent query pairs with very different run times flag potential performance bugs.
- **Ba, Rigger. CERT: Finding Performance Issues in Database Systems Through the Lens of Cardinality Estimation. ICSE 2024.** A more restrictive query should not get a larger cardinality estimate. The authors motivate the approach by the lack of any ground truth for expected execution time.
  The approach found 13 unique issues in MySQL, TiDB and CockroachDB; 9 were confirmed and 2 fixed.
- **Jiang, Zeng, Rao, Gu, Zhou, Lyu. Revealing Performance Issues in Server-Side WebAssembly Runtimes via Differential Testing (WarpDiff). ASE 2023, pp. 661–672.** The same test on different runtimes should follow an oracle ratio that reflects the systematic gaps between runtimes; cases that deviate are flagged. Seven issues were found, all confirmed by developers.
  *Relevance:* the systematic gap that WarpDiff deliberately absorbs is precisely the object our classes are about.

*Shared point:* a faster equivalent is a witness that a better time is attainable, an upper bound. None of these methods can show that no better time is attainable.

### Validity of comparisons

- **Georges, Buytaert, Eeckhout. Statistically Rigorous Java Performance Evaluation. OOPSLA 2007, pp. 57–76.** Repetition and confidence intervals; poor methodology leads to wrong conclusions.
- **Mytkowicz, Diwan, Hauswirth, Sweeney. Producing Wrong Data without Doing Anything Obviously Wrong! ASPLOS 2009, pp. 265–276** (already cited). Environment size and link order bias results.
- **Curtsinger, Berger. STABILIZER. ASPLOS 2013** (already cited). Layout randomization.
- **Bulej, Horký, Tůma, Farquet, Prokopec. Duet Benchmarking: Improving Measurement Accuracy in the Cloud. ICPE 2020.** Runs the two artifacts concurrently so that both see the same interference; accuracy improves by 2.3–12.5× on ScalaBench/DaCapo and by 23.8–82.4× on SPEC CPU 2017.
  *Relevance:* close in spirit to our counterbalanced A/A/B/B rounds.
- **Raasveldt, Holanda, Gubner, Mühleisen. Fair Benchmarking Considered Difficult: Common Pitfalls in Database Performance Testing. DBTest 2018.** Mock benchmarks show large differences where none should exist; the paper includes a fairness checklist.
- **Shypula et al. Learning Performance-Improving Code Edits (PIE). ICLR 2024.** Found that benchmarking on real hardware produced phantom improvements and moved to gem5 simulation.

### Bounds on cost, and the lineage of "certificate"

- **Williams, Waterman, Patterson. Roofline. CACM 52(4):65–76, 2009.** Bound-and-bottleneck analysis: hardware ceilings bound attainable performance, and each optimization "ceiling" must be passed to go higher.
- **Aggarwal, Vitter. The Input/Output Complexity of Sorting and Related Problems. CACM 31(9):1116–1127, 1988.** Tight lower bounds on I/Os for every algorithm in the external-memory model.
  *Relevance:* the template for our certificate, a lower bound for all algorithms in a model, with the contract playing the model.
- **Carbonneaux, Hoffmann, Shao. Compositional Certified Resource Bounds. PLDI 2015, pp. 467–478.** Worst-case resource bounds for C programs, with proof certificates.
- **Frohn, Naaf, Hensel, Brockschmidt, Giesl. Lower Runtime Bounds for Integer Programs. IJCAR 2016, LNAI 9706, pp. 550–567.** Lower bounds on the worst-case runtime of one program.
- **McConnell, Mehlhorn, Näher, Schweitzer. Certifying Algorithms. Computer Science Review 5(2):119–161, 2011.** A certifying algorithm returns, with each output, an easy-to-verify certificate; the user can trust the output without trusting the algorithm. The survey notes that primal–dual algorithms are certifying.
- **Necula. Proof-Carrying Code. POPL 1997, pp. 106–119.** An untrusted code producer supplies a safety proof that the host checks.

### Causal analysis of performance

- **Gan, Liang, Dev, Lo, Delimitrou. Sage. ASPLOS 2021, pp. 135–151.** A causal Bayesian network over microservice traces, plus a graphical VAE that generates counterfactuals ("would QoS be restored if this tier's metrics were normal?").
  The paper notes that practitioners verify root causes by reverting a service while keeping everything else unchanged, which is an intervention.
  *Relevance:* counterfactuals are modelled there. We measure ours by replay.
- Coz, Unicorn, Giamattei et al. AST'24 are already in the draft.

### Causal methods in SE and observational pitfalls

- **Berger, Hollenbeck, Maj, Vitek, Vitek. On the Impact of Programming Languages on Code Quality: A Reproduction Study. TOPLAS 41(4), 2019.** Re-analysis of an observational GitHub study: a causal link from language to code quality cannot be established from such data. The original authors dispute parts of the reanalysis; we cite it only for the methodological point.
- Furia, Torkar, Feldt TOSEM'24 (causal DAG analysis of language effects) and the other causal-SE entries are already in the draft.

### LLM agents and performance

- **Shetty, Jain, Liu, Kethanaboyina, Sen, Stoica. GSO: Challenging Software Optimization Tasks for Evaluating SWE-Agents. NeurIPS 2025 Datasets and Benchmarks.** 102 tasks from 10 codebases, scored against expert commits; leading agents succeed on fewer than 5%.
- **Shypula et al. (PIE), ICLR 2024**, above.
- Further work not cited, to save space: SWE-Perf (He et al., arXiv:2507.12415, listed in PMLR vol. 306, ICML 2026) and SWE-fficiency (arXiv:2511.06090). Both are repository-level optimization benchmarks scored against expert speed-ups.

## 3. How causal analysis helps (the argument of the paper, tied to the prior work)

1. **It makes "architectural" a well-defined quantity.**
   Prior studies call remainders inherent (Jangda et al.) or expected (Gaffney et al.) against implicit contracts.
   A declared contract defines the admissible interventions, and the residual Δ\* = inf over admissible ι of g_ι turns the label into a claim about one number with explicit scope.
   Changing the contract changes the answer, measurably (our Pair B variant contracts).
2. **It explains why the two directions need different evidence.**
   Gap-closing studies (Lee et al.; Satish et al.; PerfR) and differential testing produce witnesses, which are upper bounds.
   Only a certificate bounds the residual from below. Partial identification (Corollary 1) reports what the evidence decides and leaves the rest as candidates.
   In the synthetic check, a rule that infers "architectural" from a frozen culprit plus failed configuration fixes mislabels 19.3% of fixable gaps.
3. **It replaces bisection when there is no shared history.**
   Regression localization intervenes on history. Reimplementations need interventions on mechanisms instead, and where none can be switched, thresholds identify the effect (Theorem 2).
4. **It turns profiles into counterfactuals.**
   Replaying a cell gives Holland's "scientific solution", so per-cell shares 1 − g^σ/g are identified, not averaged.
   Profile shares and statistical rankings (APOLLO, Spectroscope) become hypotheses whose error we measure in a within-study comparison (RQ3).
   Coz already showed that profile share and optimization effect can differ, and Sage models counterfactuals rather than measuring them.
5. **It proves that passive data are insufficient.**
   Proposition 2 is a positivity failure: plans the default policy never runs are unconstrained by default-run data. So no amount of benchmarking or profiling, and no LLM explanation built only from them, can certify a class.
6. **It turns validity practices into checkable assumptions.**
   Repetition, randomized layout, duet-style pairing and fair configuration become identification conditions (temporal stability, causal transience, consistency) that RQ1 tests and known-truth controls calibrate.
7. **It makes agents' causal claims testable.**
   Optimization benchmarks (PIE, GSO) score patches. Our verdicts score the causal claims an agent makes about a gap, corrected for the procedure's sensitivity and specificity (Rogan–Gladen).
   Certificates bound what any agent could gain under the contract.

## 4. On the term "certificate"

The term is not established in software-performance or gap-analysis work, so the paper now introduces it with a definition and references (Sec. III-C).

**Where it comes from.**
- Complexity theory, where a certificate (or witness) is a checkable proof of membership.
- Optimization, where a dual feasible solution certifies a lower bound on a minimum.
- Certifying algorithms (McConnell et al. 2011), which return an easy-to-check proof with each output.
- Programming languages and verification: proof-carrying code (Necula 1997), certifying compilers, and certified resource bounds (Carbonneaux et al. 2015).
- Machine learning, as "certified robustness".

**How the paper uses it.**
- **Definition 3:** a certificate for a gap is a set of premises, each checkable against the contract, the source code or a registered measurement, that together imply Δ\*(c,s) > b.
- Theorem 1 gives one concrete form: chokepoint, envelope and floor.
- The paper states the duality analogy: witnesses bound the infimum from above like feasible solutions, certificates bound it from below like dual solutions.
- It names the lower-bound template (Aggarwal and Vitter: a bound for all algorithms in a model, with the contract as the model).
- It names the reason checkability matters: agents propose the premises, and a checker verifies them without trusting the producer, as with proof-carrying code.

**Terminology caveat.**
In complexity theory, "witness" and "certificate" are synonyms. We use "witness" for the existential side (a fix exists) and "certificate" for the universal side (no admissible fix gets below the band). The duality sentence makes the asymmetry explicit.

**If you prefer another name.**
- "Lower-bound certificate" (most explicit).
- "Floor certificate" (matches condition C3).
- "Architecture certificate" (matches the class, but suggests certifying the architecture rather than the bound).

Either of the first two would be a global rename in the paper and in `theory/`.
